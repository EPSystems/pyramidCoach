# Decisions

Every judgment call made while building Pyramid Coach from `PyramidCoach_PLAN.md`. Newest last.

## Platform & tooling
1. **Next.js 16 (App Router).** `create-next-app` installed v16, where middleware is called `proxy.ts`. The template enabled `cacheComponents` and `partialPrefetching`; both are **off** because every screen is per-user, RLS-backed and dynamic.
2. **Zod 4.** `z.uuid()` enforces RFC variant bits, but seeded exercise IDs are `md5('ex:'||slug)::uuid` (deterministic, idempotent seeds), which are not RFC-variant. Actions validate IDs with `z.guid()`.
3. **shadcn/ui "radix-nova" preset**, with buttons enlarged to a ≥44 px tap height (Section 8). Theme handled by a small in-house provider instead of `next-themes`; **dark is the default**, light/system are opt-in in Settings.
4. **Design language "chalk & steel":** graphite surfaces, hi-vis volt accent, Big Shoulders (display), Archivo (body), JetBrains Mono for rule-ID "stamps". Chart colours were validated with the dataviz palette validator for both themes (`--chart-1/2`).
5. **Local-first verification.** Built and verified against the local Supabase stack (Docker). Cloud Supabase/Vercel deployment needs the owner's accounts and was not done by the agent (see README → Deploy).

## Data model additions (beyond Section 5)
6. `exercises.slot_tags`, `exercises.popularity`, `exercises.mistakes`: needed to fill session-template slots deterministically (Appendix D) and for the library's "common mistakes".
7. `user_settings.split_style`, `strength_lifts`, `disliked_exercise_ids`, `e1rm_seeds`, `target_adjustments`, `trained_last_month`, `status_history`.
8. `nutrition_settings.kcal_offset` (cumulative accepted calorie changes, so recomputes after sport/bodyweight changes keep them), `initial_adjust_done`, `phase_history` (4:1 tracker).
9. `planned_exercises.slot_key`, `skipped`, `rule_ids`; `planned_sessions.started_at/finished_at`; `blocks.schedule/selections/explanations/warnings/median_target`; `proposals.preview`.
10. `profiles.email`, `bodyweight_kg`, `hide_bodyweight`, `last_active_at`. `app_config` (owner email) is readable only by security-definer functions.
11. **Idempotent set logging:** unique constraint `(planned_exercise_id, set_index)`; NULL planned ids never conflict.
12. Plan materialisation is one Postgres function, `replace_future_plan` (security invoker, so RLS still applies), giving the "one transaction" of Section 6.14. Accepting proposals applies their diff with sequential RLS-checked writes.

## Engine
15. **Exercise `equipment` = any-of.** An exercise is feasible if the user has any listed item (e.g. Bulgarian split squat: dumbbell, bodyweight or barbell).
16. **Extra exercises** beyond Appendix E (dumbbell RDL, single-leg RDL, dumbbell fly, DB rear-delt fly, DB overhead triceps, single-leg DB calf raise, inverted row, band pull-apart), so the dumbbell and bodyweight presets work. 74 exercises total.
17. Face pull keeps the Appendix E roles (back primary) but is **not** used for the "rear-delt iso" slot.
18. **Time check (6.3 / T-SCH-01):** a split fits if the *average* session ≤ session length and no single session exceeds it by more than 15%. Upper/Lower splits are naturally upper-heavy; the plan's own G4 expectation (4 days at 60 min) only holds under the summed/average formulation.
19. **Distribution:** sets are spread to another session (adding an isolation where the muscle isn't trained yet) before an exercise goes past 4 sets; ties go to the shorter session. Front delts are never trimmed for being over target (pressing covers them).
20. **Within-week variety:** an exercise already used elsewhere in the week is mildly deprioritised (after tag and category preference).
21. **Scheduling penalties added:** lifting on the same day as a `moderate` sport +2. A `morning` sport counts as "before lifting" (+3), since lifting time isn't collected. A leg session on the same day as a leg-heavy hard sport costs +1. With these, G4 resolves to Mon Upper / Wed Lower / Thu Upper / Sat Lower (legs on the match day, flagged on Today), which is what the plan's G4 constraints allow.
22. **Strength goal** always uses the default (FB/UL) splits, because only they carry main-lift slots; k ≤ 5 days. Load-phase supporting volume starts at 10 and drops 1 set/week (floor 5). Back-offs are at RPE 7.
23. **Intro week (T-FAT-06)** at onboarding is triggered by a "Trained regularly in the last month?" answer, since a fresh start has no history.
24. **Block start:** a new user's first block starts this Monday if today is Mon–Wed, otherwise next Monday (sessions before today are not created). Regenerations start at this Monday and replace sessions from **today** (not tomorrow) unless today's session is already started or done.
25. Hypertrophy and sport-support blocks are 6 weeks.
26. **Targeted deload:** for a muscle, remove exercises where it is primary and the exercise is axial/impact/free-weight compound; halve the sets of the other exercises where it is primary. For `erectors` (lower back), remove every axial exercise.
27. **Nutrition initial adjustment (N-ADJ-01):** compares phase week 1 with the week before; with no prior data (new users), compares week 2 with week 1. Maintenance drift step is 125 kcal.
28. **Body map geometry:** the unnamed lumbar strip maps to `erectors` and the inner-thigh strip to `adductors`, so lower-back soreness can be tagged (G8). The shin strip stays decorative.
29. Readiness pill on Today is an APP heuristic: sleep ≥ 7 h, energy ≥ 3, stress ≤ 3, no pain.
30. In-session suggestions (6.10) are computed when the logger opens from the latest history, rather than frozen at plan generation; logging them is the approval.
31. "Why?" explanations reuse the rule registry's own-words summaries, with bespoke lines for the most common rules (`lib/knowledge/explanations.ts`). No book text anywhere.

## Auth (open sign-up, 2026-10-25 — replaces 13; see `docs/AUTH_PLAN.md`)
32. **Open sign-up.** Anyone can create an account with **Continue with Google** or **email + password** (≥ 8 chars, letters and digits; same rule in Supabase and zod). The `invites` table, `enforce_invite` trigger and `is_invited()` are dropped (`20261025151754_remove_invite_only`). Sign-in no longer sends an email, which also removes the per-login email rate-limit problem. The owner is still whoever matches `app_config.owner_email`; admin keeps the users list and **Remove user** (`admin_remove_user`).
33. **A profile exists only after confirmation.** `handle_new_user` runs on `insert or update of email_confirmed_at` when it is set, instead of on every insert. Google users arrive confirmed and get a profile at once; email sign-ups get one when they click the link. Unconfirmed sign-ups have no app data and don't appear in Admin. `display_name` comes from Google's `full_name` when present.
34. **Email links use `token_hash`, not PKCE.** The confirmation and recovery templates link to `/callback?token_hash=…&type=…`, which `verifyOtp` accepts in any browser. That matters on Android, where Gmail opens links in its own in-app browser that doesn't have the PKCE verifier cookie. Local `config.toml` uses the same templates (`supabase/templates/`).
35. **Google is auto-linked by email.** Supabase links a Google identity to an existing user with the same *confirmed* email, so the owner's old magic-link account keeps its data when signing in with Google (or after setting a password via *Forgot password*).
36. **No account enumeration.** Sign-up with a registered email shows the same "Confirm your email" screen; wrong password and unknown email get one message; forgot-password always answers "If an account exists…". Redirects only follow a same-site relative `next` (`safeNext`), and links are built from `APP_URL` or the request origin, never `localhost` in production.

## Weekly review, proposals and fatigue (2026-10-27)
37. **RIR drift** (APP from T-RIR-01 / T-FAT-01, `rirDrift`, `RIR_DRIFT`): an exercise drifts when its first working set ended at least 1 RIR below the prescribed floor on its last 2 exposures (the latest in the reviewed week) with no load jump above +2.5% between them. Two or more drifting exercises answer "performance down" yes, alongside the reps-at-same-load and e1RM checks. Logged sets carry the planned `rir_min` via the `planned_exercise_id` join; ad-hoc sets are ignored.
38. **Low readiness prompts the light swap** (T-FAT-08, `lighterSessionFor`): when today's readiness score is ≤ 1 ("Take it easy") and a lighter planned session remains this week, Today shows a prompt with the existing swap button. Nothing changes until the user taps it.
39. **Plan-level proposals** (`lib/engine/plan-review.ts`):
    - `injury_adjust` (T-SEL-08): (a) a non-resolved injury whose avoid list, or for pain/injury severity axial/impact work on the area, is still in the upcoming plan; (b) pain tagged on one area on ≥ 2 days in the 14 days ending with the reviewed week while the plan still has "remove"-class exercises for it (T-FAT-04 classification). Accepting (b) logs a new injury (severity pain, avoid list = those exercises) or raises an existing niggle to pain, then regenerates. Resolved injuries get no proposal: the plan already regenerates on resolve and avoided exercises return at the next block (T-SEL-06).
    - `volume_change` (T-FAT-02/03, T-VOL-07): two reviews in a row with ≥ 2 yes answers → −2 weekly sets on muscles at ≥ 10 sets (floor 4). Upward volume changes stay with `plateau_action` add_volume (T-VOL-07 only allows more sets after a plateau).
    - `exercise_swap` (T-SEL-04 / T-SEL-06): a disliked exercise still planned → best feasible substitute; a stalled lift whose muscles are already at the 20-set cap → a close variation (same main lift for the strength goal).
    - `plan_regenerate` (T-SCH-01 / T-SEL-04): the plan drifted from settings (2+ sessions next week on unavailable days, or planned exercises needing missing equipment), i.e. a settings save whose automatic rebuild failed.
    - `intro_week` (T-FAT-06): no working set for 14+ days (or a 14+-day-old block with nothing logged) and the upcoming week isn't already intro/deload.
40. **T-FAT-05 higher-rep week** is a second `targeted_deload` proposal with `mode: 'higher_reps'`, offered when aches are flagged and next week loads the area with compounds. It keeps sets and moves those exercises to `HIGHER_REP_WEEK` ranges (above each T-INT-03 range, inside T-INT-01's 4–30). The apply path writes `rep_min/rep_max`.
41. **Rehab and niggle notes** (T-SEL-08, `injuryNote`): planned exercises that mainly train an area in rehab get "lighter load and higher reps (12–20), stop well short of pain"; a niggle area gets "keep every rep pain-free". The body map shows only active/rehab injuries, with the injury's note.
42. **Untracked muscles** on the body map point to the tracked group that trains them (`INDIRECT_VIA`: traps → back, forearms → biceps, lower back → hamstrings, adductors → quads); abs get plain copy.
43. **Status inference is one row per week**: `weekly_reviews.inferred_status` (migration `20261027150001`) replaces appending to `user_settings.status_history` (left in place, no longer written). Both `weeklyReview` and `submitReview` use `statusAnchorIds` (main lifts + session anchors). "Two in a row" compares with the latest earlier week that has an inference.
44. **Plateau targets** come from the reviewed week's block week (clamped into the block), not week 0.
45. **Duplicate proposals**: keyed by kind plus target (`proposalKey`: plateau exercise, targeted-deload mode, swap source, injury/muscle). Same key and same payload (`stableJson`) → the new one is dropped; different payload → the new one is inserted and the stale pending one becomes `superseded` (new proposal status).
46. **Accepting fix_basics** changes no plan rows; the accepted proposal is the record, and Today shows its basics checklist for 7 days after `decided_at`.
47. **Nutrition notes** (`nutritionReviewFor`) are shown on the review page as "Nutrition check"; a failed read hides them.
## Nutrition & progress gaps (2026-10-27)
37. **Weigh-ins rebase the targets.** `logWeighIn` (and a check-in that carries a weight) calls `refreshTargetsAfterWeighIn`. It recomputes when the bodyweight the targets use (mean of the last 7 weigh-ins) has moved by ≥ 0.5 kg since the newest `nutrition_targets` row, which now stores that weight in `bodyweight_kg` (migration `20261027160001`; older rows are null and refresh on the next weigh-in). The threshold is an APP choice: smaller moves change kcal by < ~20, so daily noise doesn't create a new row every morning. This is a base recompute only: it keeps the accepted `kcal_offset` and never touches `last_adjusted_on`/`initial_adjust_done`, so trend-based rate adjustments still follow N-ADJ-01/03 (14-day wait, first-week check). A failed refresh never fails the weigh-in. Users without `nutrition_settings` (not onboarded) are skipped.
38. **Recalculate on /nutrition** calls `refreshNutritionNow`, a rebase with the same cadence rules as 37 (no threshold, always writes a row).
39. **Sport calories use logged session RPE where it exists (N-SPT-01).** Frequency still comes from the weekly schedule (N-SPT-03 stays a weekly average added to every day), but the energy of one session comes from the mean of that sport's `sport_logs` in the last 28 days once at least 3 of them have a session RPE (`sessionKcalFromRpe` factors: RPE ≤ 4 light, ≤ 7 moderate, else vigorous). With fewer rated logs the declared minutes × intensity is used. Per-day targets from individual sessions were rejected: logs arrive after the day's target is set and sparse logging would swing targets. Logging a sport doesn't recompute by itself; the next recompute (weigh-in, Recalculate, settings change) picks it up.
40. **Lifestyle change = rebase, not an adjustment.** `recomputeNutrition(…, { multiplier, rebase: true })` from the lifestyle setting resets the activity factor to the new default but keeps `last_adjusted_on` and `initial_adjust_done` (`nextAdjustState`). Before, it set both, which started a 14-day wait and silently skipped the N-ADJ-01 first-week check. Only accepted proposals (a `kcalOffsetDelta`, or a `multiplier` without `rebase`) count as trend adjustments. The accepted kcal offset is kept across the rebase.
41. **One source for target rates.** `allowedRatePcts(phase, status)` drives the picker and `rateError` the server: loss 0.5/0.75/1 %/week (N-RAT-01), gain = the options 0.25/0.5/1/1.5/2 %/month inside the status range (N-RAT-02: novice 1–2, intermediate 0.5–1.5, advanced 0.25–0.5). The Zod schema caps at the widest allowed rate (2); `updatePhase` reads the training status and rejects anything else.
42. **4:1 stays guidance.** N-PHS-02 says to spend at least 4× as long building/maintaining as cutting; the book frames it as a planning guideline, and blocking a cut (e.g. for a weigh-class or a medical reason) is a product call. The bar stays, and switching to a cut that would break 4:1 now returns an explicit warning toast (`cutRatioWarning`) instead of being enforced.
43. **e1RM rule `T-EST-01` (GEN).** The progress "How?" link cited T-STR-01 (strength phase cycling). It now cites a new general-knowledge rule describing the Brzycki-style estimate on reps + RIR and the 12-rep cutoff (also added to `seed.sql`; re-run `pnpm seed:gen` to confirm it matches). `lib/engine/strength.ts` is still not used by /progress: phase RPEs belong to the plan/Today screens, and the page has no block-phase context worth repeating.
44. **Progress history range.** `/progress?range=3m|6m|1y|all` (default 6m) applies to the e1RM charts, exercise history, bodyweight and adherence. Weekly sets stay an 8-week view. Reads go through `lib/server/progress.ts` and `fetchAllPages`, which pages past PostgREST's 1000-row `max_rows` (the old 180-day query could already be cut off silently), selects only working sets, and orders by a unique key. Adherence is weekly for 3 months and monthly beyond.
45. **High-rep exercises get a trend.** Exercise history uses first-set e1RM when at least half the days have one; otherwise volume load (Σ load × reps) for loaded work or total reps for bodyweight work, labelled on the chart. The chart now shows the user's unit.
46. **Stall flags on /progress** are read-only: the weekly review's `isPlateaued` test on each main lift's pooled best-e1RM series over the last 26 weeks, independent of the selected range. The review still owns plateau proposals.
47. **CSV exports:** `/api/export?format=csv&type=sets|weighins|checkins|nutrition` (`sets` is the default, so old links work); JSON stays the full export. Every table is paged so exports over 1000 rows are complete. The download links live on /progress ("Your data"); Settings keeps its two existing buttons.
## Session logger (2026-10-27, PROGRESS §4 gaps)
37. **Warm-ups are logged.** Each ramp set (T-WUP-01) has its own tick and is stored with `is_warmup = true` and its own `set_index` sequence (0, 1, 2), so the idempotency key is now `(planned_exercise_id, is_warmup, set_index)`. Every analytics path already drops warm-ups (`setCounts`, `exposuresFor`, `bestRecentE1rm`, fatigue, plateau, status, body/progress/library pages, `v_weekly_muscle_sets`, the new history RPCs); the CSV export keeps them with a `warmup` column.
38. **Rest timer persists in `localStorage`, not the database.** The logger stores the running timer's start timestamp, target and exercise under `pc:rest:<sessionId>`, restores it on reload (ignored after 30 min or if malformed) and clears it on dismiss or finish. Nothing reads actual rest times yet, so no column was added and `logSet`'s payload stays as is (the offline queue wraps it).
39. **`planned_exercises.label` holds engine text, `note` only the user's note.** "Top single @ RPE x" / "Back-off sets @ RPE x" are written to `label` by `replace_future_plan`; the note dialog edits `note` only. Back-off loads are recognised by the prescription's rule (`T-STR-03` on a non-single), with the label as a fallback, never by note text. The migration moves existing labels out of `note` and rebuilds ones a user note had overwritten from `10 − rir_min`.
40. **Finish screen**: muscle chips cycle none → sore → pain. If saving the tags fails, the session is not finished silently: an inline error offers *Try again* or *Finish without tags*. "Sets this week" shows the week's counted sets per muscle (other sessions from the server + this session live), with today's share in brackets.
41. **`swapExercise` re-checks the target server-side** with `swapOptions` (`lib/engine/swap.ts`, the same top-8 `substitutionsFor` list the dialog shows: same primary muscle, equipment, injuries, dislikes).
42. **"Add set" cap = 11 per exercise** (`FREQUENCY.maxSetsPerMusclePerSession`, T-FRQ-01): every set of an exercise trains its primary muscle, and past ~11 sets per muscle per session extra sets are junk volume. The server refuses past the cap with that reason and the menu item shows "Max 11 sets".
43. **Logger history is targeted, not capped.** `session_exercise_history(session, n)` returns working sets from the latest *n* training days of each exercise in the session (other sessions only); *n* = max(3, 2 × T-PRG-06 pace for the user's status). `session_exercise_best_e1rm(session)` aggregates the all-time best e1RM in SQL for the PR baseline (same Brzycki-on-effective-reps formula as `e1rm.ts`; keep the two in sync).
44. **T-PRG-06 in the logger**: `suggestNextSession` takes an optional `status`. When the suggestion keeps the load and the exercise has been at that load for ≥ 2 × the expected sessions per jump (novice 5, intermediate 10, advanced 20; APP factor, since single flat sessions are normal per T-PRG-05), it adds `T-PRG-06` and a hint to check that set 1 really reaches the top of the range at the top RIR. Programme changes for a real stall stay in the weekly review's plateau flow.
45. **Today/logger data loading**: the session page loads in one round after the user context (session, catalogue, history RPCs, this session's sets, this week's sets in parallel; before: four sequential rounds and a 600-row read). Today selects only the block and session columns it renders instead of `blocks.*` (large JSON) and `planned_exercises.*`.
## Onboarding (2026-10-27)
37. **Onboarding data is written by one RPC, `complete_onboarding(p jsonb)`** (security invoker, so RLS applies; migration `20261027110001`). It locks the profile row, refuses with hint `already_onboarded` once `onboarded_at` is set, then updates the profile, upserts settings, replaces sports/custom sports/injuries (delete + insert) and upserts today's weigh-in, all or nothing. The rows are derived in TypeScript (`lib/onboarding/derive.ts`, pure and tested); the first plan and nutrition targets are still built in TypeScript afterwards, and `onboarded_at` is still set last, so a failed build leaves the user on the wizard and a resubmit simply replaces the data. Before onboarding completes, a user's own custom sports can only come from an earlier attempt, so the RPC deletes them and the wizard lists catalog sports only.
38. **"Not sure" experience can yield advanced (T-STA-02):** under 1 year → novice; 1–5 years → intermediate; 5+ years asks "Do your heavy lifts still go up month to month?", where "Barely" → advanced and "Yes" → intermediate. Years alone never give advanced, because status is about rate of progress (T-STA-01).
39. **The wizard sends kg and cm.** Like bodyweight, best-set seed loads are converted from lb before the payload is sent (`seedsToKg`), and lb users enter height in feet + inches (`cmFromFtIn`, stored to 0.1 cm). Switching units carries the height across; bodyweight and seed values are not rescaled (their labels follow the unit, as before). Birth year, height, bodyweight, body fat and sport minutes are checked in the browser with the same zod field schemas the server uses (`lib/schemas/onboarding.ts`), so the messages match.
40. **Owner pre-fill lives in `lib/onboarding/owner-prefill.ts` (`OWNER_PREFILL`, `prefillFor(role)`)** and now includes sex (`male`). Appendix F says "(ask)", so it is only pre-selected and stays visible on step 1 to confirm. Injuries added in the wizard can be marked "Hurting now" (`active`) or "In rehab" (`rehab`) and can list exercises to avoid: suggestions are exercises whose primary muscle is the injured area, plus a name search over the whole catalog.
## Accounts & platform (2026-10-27)
37. **Owner-appointed admins.** Roles are `owner` (still the one `app_config.owner_email`), `admin` and `member`. Admins open `/admin`, see the user list and edit global exercise text; only the owner promotes/demotes (`admin_set_role`, security definer, checks `is_owner()`) and removes users. The owner role can't be granted, changed or removed in the app, and `admin_remove_user` now also refuses any row holding the owner role. Admin powers were added as *extra* permissive policies (`is_admin()`), so the owner policies are untouched.
38. **`lib/supabase/admin.ts` deleted.** Nothing in the app used the service-role client since invites went away, and every privileged step is a security definer function behind a role check. Tests and e2e create their own service-role client from env; keeping an unused service-key client in the app only widened the attack surface.
39. **Cascades verified by introspection.** `auth_user_fk_report()` (service role only) lists every FK to `auth.users` with its on-delete action; `tests/integration/accounts.test.ts` asserts all cascade, seeds a row into every listed table, deletes the user and checks zero rows remain, so a new user table without a cascade or seed fails the test. Unconfirmed sign-ups older than 7 days are deleted nightly by `purge_unconfirmed_users()` via `pg_cron` (job `purge-unconfirmed-users`, 03:17 UTC), scheduled only when the extension is available and never failing the migration.
40. **Theme follows the account.** `profiles.theme` (null until chosen) is written when the user picks a theme in Settings; `ThemeSync` in the app layout applies it on other devices. localStorage `pc-theme` stays the pre-paint cache, so a known device never flashes; a brand-new device paints its default once, then switches.
41. **Return to the requested page.** The proxy sends signed-out visitors to `/login?next=<path+query>` (`loginRedirect`, validated by `safeNext`; nothing for `/`, `/today` or `/reset-password`). Password sign-in and Google already honour `next`; email sign-up keeps `/onboarding` because new users must onboard first. A signed-in user on `/login?next=…` goes straight there.
42. **Weight jumps in the user's units.** Increments stay stored in kg; Settings shows and accepts them in the *saved* units (lb rounds to 0.1, stored back to 0.01 kg), using string drafts so half-typed input like `2.` isn't swallowed.
43. **Body changes recompute nutrition.** Changing sex, height or body fat in Settings runs `recomputeNutrition` with no overrides (phase, multiplier and accepted offsets kept); a lifestyle change in the same save already recomputes with the new multiplier.
